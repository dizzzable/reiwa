# Reiwa v0.9.7.15

Кабинет переставал открываться примерно раз в сутки. Здесь причина и две стены против неё. Парная версия панели не менялась — **[Rezeis Admin v0.9.7.20](https://github.com/dizzzable/rezeis/releases/tag/v0.9.7.20)**, обновлять её не нужно.

> **Нажимать в интерфейсе ничего не надо.** Достаточно обновить образ. Отдельно, по желанию, можно заменить конфиг обратного прокси — он в образ не входит, подробности в конце.

## 🚪 Почему входная дверь вставала раз в сутки

Симптом выглядел как беда прокси: браузер получал `504 Gateway Time-out`, помогал перезапуск контейнера с nginx. Прокси оказался ни при чём.

В журнале приложения нашлась асимметрия, которая и была диагнозом:

```
GET /              → держится 60006 мс, обрывается без кода ответа
GET /api/v1/*      → 200 и 304 за единицы миллисекунд, в те же секунды
```

Шестьдесят секунд — это **терпение прокси**, а не предел приложения: само оно ждало бы вечно. А маршруты API отвечали потому, что отдают из внутрипроцессных кэшей. Документ страницы — единственный путь, который **до первого байта** читает снимок оформления оператора из Redis.

**Первопричина.** Все три клиента Redis создавались без `commandTimeout`. У ioredis это умолчание значит буквально следующее: команда, записанная в сокет и оставшаяся без ответа, ждёт без срока. Сокет при этом выглядел живым — `ESTABLISHED` с нашей стороны и мёртвый с другой. Простаивающее соединение подрезает межсетевой экран или таблица трансляции адресов; отсюда и суточный ритм. Ошибки не возникало **вообще**, поэтому обрабатывать было нечего, а отказ два дня оставался невидимым.

Теперь у команд есть срок — 2 секунды, с запасом на любой здоровый обмен, — и `keepAlive` 30 секунд вместо умолчания системы около двух часов. Мёртвый сокет обнаруживается, пока соединение ещё простаивает.

## 🧱 Вторая стена: документ больше не ждёт никого бесконечно

У страницы было **два** ожидания без срока — снимок оформления и поиск лендинга. Вокруг обоих стоял `try/catch` с комментарием «never fail a document over a favicon». Про **отказ** это было правдой. Про **ожидание** там не было сказано ничего, а случилось именно оно.

Оба ожидания получили срок в 1,5 секунды, и оба отсчёта стартуют одним тиком — поэтому худший случай документа равен одному сроку, а не двум подряд.

Полторы секунды выбраны так, чтобы годились **оба** способа развернуть кабинет:

- панель на **том же** сервере — ответ за единицы миллисекунд, срок не срабатывает никогда;
- панель на **своей** VPS — всё ещё далеко внутри здорового обмена.

Дальше система не медленная, а больная. Тогда страница отдаётся **без** знака оператора: приложение подставит его сразу после загрузки, и подписчик получает рабочий кабинет вместо бесконечно крутящейся вкладки.

Истёкший срок пишет предупреждение в журнал. Это половина исправления: зависание не порождает ошибки, и без этой строки следующий такой случай снова был бы невидим.


**Мутацией: 3 из 3.** Убрать срок — падает тест «отдаёт запасной вариант, когда ожидание не заканчивается», причём **по таймауту**, то есть боевое зависание воспроизводится в миниатюре. Убрать срок команды — падает тест настроек. Собрать один клиент Redis по-старому — падает сторож, который проверяет **все** места создания клиентов, а не три известных: защищать надо от четвёртого, добавленного позже.

Сторож на первом же прогоне поймал ложное срабатывание — на собственном комментарии — и был сужен так, чтобы срезать комментарии, но не резать строку кода: наивная версия сделала бы невидимым как раз того нарушителя, который больше всех похож на настоящий код.

## 🔧 Отдельно: конфиг обратного прокси

В журнале nginx нашлось второе, не связанное с отказом: **каждый** ресурс каждого посетителя спускался во временный файл на диск — по строке `an upstream response is buffered to a temporary file` на каждый чанк сборки, стиль и знак.

Причина — буферы по умолчанию, 8 по 4 КБ, тогда как любой ресурс кабинета крупнее. Конфиги в `deploy/proxies/` (nginx и angie) получили буферы под реальные размеры и `proxy_max_temp_file_size 0` — «только память, дальше отдавать в темпе клиента». Защита от медленного клиента сохраняется, диск больше не участвует.

**Конфиг в образ не входит.** Если хотите это исправление — замените файл целиком и перечитайте конфигурацию:

```bash
docker exec <контейнер-nginx> nginx -t
docker exec <контейнер-nginx> nginx -s reload
```

Менять по частям не стоит: правка одного блока уже однажды унесла закрывающую скобку вместе с разделом TLS.
